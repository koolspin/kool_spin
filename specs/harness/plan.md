# Plan: harness

Written by the planning pass from `spec.md`. Each build pass takes the first unchecked task, ticks it when every check passes, and adds a note beneath it. A failed attempt is recorded as a note; three failed attempts on one task mean the loop writes `BLOCKED.md`.

The API (`src/apps/harness/include/ks/harness/*.h`), the stubs, `main.cpp`, and the codec library (`third_party/miniaudio/`, `ks_codecs.h`) already exist. The tasks fill in the stubs. Don't change the public headers' declarations: the acceptance tests are written against them. Private helpers go in private headers in `src/apps/harness/` (not under `include/`). Unit tests go in a new `tests/harness/` directory, registered as `ks_harness_tests` with `ks_add_test()` in `tests/CMakeLists.txt` (not protected), linking `ks::harness`.

## Decisions

- **Cue points and seeks on file tracks:** requirement 11 says every command is checked with `decode()` when the script is read, but a file track's rate isn't known until it's decoded (requirement 6 forbids opening files while reading). The reader checks a `TrackTime`'s frame with `decode()` when the deck's track is synthetic, and otherwise only that the seconds form a valid amount (`decode()` accepts any finite, non-negative frame, so a non-negative amount within limits will decode at any track rate). Task 3's builder should confirm this against `src/engine/command.cpp` and record it in Learnings if the engine's limits differ.
- **Repeat-block time limits:** times inside an expanded block are checked against the 86,400 s limit and the `end` like any other event; an error there names the inner line.
- **Determinism:** file mode uses a fixed `start_time` (the epoch of `steady_clock`) so host times, and anything derived from them, are the same on every run. Render loads vary run to run but don't touch the audio.
- **Unit tests** live in `tests/harness/`, separate from the acceptance tests, so each pass can add its own checks without touching protected files.

## Learnings

What a later pass, or the maintainer, should know.

- The acceptance tests are the Catch2 test cases in `ks_harness_acceptance_tests` plus the `ks-harness.*` command-line cases; `ctest --preset debug -L acceptance -R harness` shows where they stand.
- `render_offline()` writes non-interleaved per-channel buffers; the WAV writer wants interleaved samples.
- On macOS `std::uint64_t` is `unsigned long long`: name the type in `std::min`/`std::max` with frame counts.
